# Contributing

## Two branches

| Branch | What it is |
|---|---|
| `dev` | Where the work happens. Bundles, `utils/`, this file. Always branch from here. |
| `main` | What people deploy from. One commit per publication, generated by `utils/publish.sh`. Never commit to it by hand. |

`main` is not a merge of `dev`. Each publication is a single commit whose tree is `dev`'s tree
minus everything [`.mergeignore`](.mergeignore) names, so no development history and no
excluded file ever becomes reachable from `main`. `git log --oneline main` reads as a list of
publications.

Both branches live on the same public remote, so nothing here is private: `.mergeignore` keeps
maintenance files out of what people *deploy*, not out of what they can *see*.

## Publishing

```bash
git switch dev                       # publish.sh refuses if main is checked out
./utils/publish.sh --dry-run         # review the snapshot, the tags, and the message
./utils/publish.sh                   # or --edit to revise the message first
```

Then push what it prints: `main`, the new tags, and `dev`.

The script builds the snapshot in a temporary index, so no branch is checked out and your
working tree never moves. It refuses to run with uncommitted changes, refuses if `main` is
behind its remote, and validates every bundle *in the filtered snapshot* by loading it with
`boff deploy --dry-run`. That last check is the important one: it is what catches a
`.mergeignore` pattern that quietly guts a bundle.

Useful flags: `-n/--dry-run`, `--edit`, `-m` to replace the subject, `-f/--force` to override a
guard, `--skip-checks` to skip validation, `--amend` to replace a publication you have not
pushed yet.

## Versions and tags

Every bundle carries its own `meta.version`. When a publication includes changes to a bundle,
the script tags that bundle `<bundle>/<version>` — for example `writing/0.1.0` — so a user can
pin it:

```yaml
extends: https://github.com/atom-sw/bun-off-bundles.git/writing@writing/0.1.0
```

**Bump `meta.version` in the same change that edits a bundle.** If a bundle changed since the
last publication and its tag already exists, publishing refuses and names it. There is no
changelog here, so that guard is the only thing keeping the tags meaningful.

Use semantic versioning as it applies to a bundle: a new rule or skill is a minor bump, a
reworded rule is a patch, and removing an artifact or changing what a bundle targets is a major
one.

One thing the guard cannot see: `general-dev` extends `commons-dev`, so a change to
`commons-dev` alters `general-dev`'s behaviour without touching a single file in it. Bump
dependent bundles by hand when the change is worth it.

## The vendored skill

`writing/skills/simple-english/` is copied verbatim from
[SimpleEnglish](https://github.com/AminBlg/SimpleEnglish) (MIT) and pinned to a commit recorded
in that folder's `UPSTREAM.md`. Do not edit those files: change them upstream, or refresh the
copy.

```bash
./utils/sync-simple-english.sh --check   # has upstream moved?
./utils/sync-simple-english.sh           # copy, then review with git diff
```

Read the diff before committing it. That text lands in the context of every project the bundle
is deployed to.

## Adding a bundle

A bundle is a directory with a `boff.yaml`; the publish script finds it by that file alone, so
nothing needs registering. Give it a `README.md`, a `meta:` block with `name`, `description`,
`long_description`, `version`, and `author`, and add a row to the table in the root
[`README.md`](README.md).

Deploy it somewhere disposable and run `boff check` against it before publishing. The
`bun-off-bundle` bundle in this repository teaches the manifest format if you need it.
